# Fantasy Manager Modding Devkit — Web App Design

**Date:** 2026-06-10
**Status:** Approved for planning
**Replaces:** `devkit/fantasy_manager_editor_v6.py` (PyInstaller `.exe` — triggers AV false positives)

---

## 1. Summary

A static, browser-based modding tool that replaces the current Tkinter+PyInstaller devkit. It targets non-technical modders with a recipe-driven wizard UX, while keeping a full-fledged editor for advanced users. Distributed three ways from a single source: GitHub Pages, offline ZIP in releases, and a folder bundled with the game.

Output is written as new JSON files with mod-name prefix into the same folder structure the game already globs (`game/data/workers/*.json`, `game/data/events/*.json`, etc.). Existing game files are never modified.

## 2. Goals

- **Zero antivirus friction.** No `.exe`, no PyInstaller. Pure HTML + JS + CSS, runnable by double-clicking `index.html`.
- **Friendly to non-technical modders.** Recipe-based wizards (one question per screen, tooltips, live JSON preview) cover common authoring tasks: new worker, event chain, daily story with trait roll, etc.
- **Power-user friendly.** Free editor for fine-tuning generated JSONs or editing existing files, with wizard-style section navigation that allows direct jumps.
- **Live catalogs.** Trait/item/building dropdowns reflect the user's actual installed game (including other mods), with bundled snapshot fallback.
- **Full Whoremaster→Fantasy Manager import.** Parity with the v6 importer (XML parsing, skill/trait mapping, image rename, GIF→WebM) plus per-character preview and unknown-trait resolution UI.
- **Safe by default.** Mod output uses prefixed filenames in mirrored folder structure; existing game files are never overwritten; merge happens only inside the modder's own mod files.

## 3. Non-goals

- **No runtime mod manager inside the game.** The game already globs `*.json` per data folder — that is the integration surface. The devkit only generates files; the game loads them.
- **No multi-user / cloud sync.** Single-user, local-first.
- **No live game scripting.** The devkit only produces JSON content, not Ren'Py code.
- **No support for partially-overwriting base game entries via runtime merge logic in the game.** Build-time merge happens only when the modder edits their own previously-generated mod files.

## 4. Architecture

### 4.1 Stack

- **HTML + CSS + vanilla JS + lightweight Web Components.** No React/Vue/build step. ES modules served as-is.
- **Persistence:** File System Access API (Chrome/Edge/Brave) for read/write directly into the user's game folder. Drag-and-drop + ZIP download as Firefox/Safari fallback.
- **UI preferences:** `localStorage` (last mod name, NSFW visibility toggle, language).
- **ffmpeg.wasm** lazy-loaded only when the GIF→WebM tool is opened. Bundle cached in IndexedDB for offline reuse.

### 4.3 High-level user flow

1. Open the app → landing screen: **Select game folder** (recommended) or **Continue without folder** (uses bundled catalog snapshots, banner warns about staleness).
2. Choose an action tile:
   - **Create with a recipe** (guided wizard)
   - **Edit existing content** (open a JSON file)
   - **Import from Whoremaster** (XML batch importer)
   - **Image utilities** (batch rename, GIF→WebM, worker-from-folder)
3. Provide a **mod name** once per session (defaults to last-used). All generated files use it as a prefix.
4. On save: app writes to `<game>/game/data/<type>/<filename>.json`. If the target file already exists, the new entry is **merged** (appended to the array or merged by `id`) — never overwritten blindly.

## 5. Recipes (guided wizards)

Each recipe is a declarative module describing ordered steps, field-to-JSON mappings, and a final review screen. A single generic engine renders all recipes.

### 5.1 Recipe definition shape

```js
export const unique_worker_recipe = {
  id: "unique_worker",
  title: "Unique Worker (Aelis/Yvara style)",
  description: "Generates a worker with a fixed name, encounter_only, dedicated image folder",
  default_output: "workers/workers_<modname>_unique.json",
  steps: [
    { id: "name",          type: "text",     label: "Worker name", required: true },
    { id: "folder",        type: "text",     label: "Image folder name",
                           hint: "Must match images/workers/<folder>/" },
    { id: "nsfw",          type: "bool",     label: "NSFW content?", default: false },
    { id: "gender",        type: "select",   options: ["female", "male"] },
    { id: "race",          type: "catalog",  catalog: "race_traits" },
    { id: "extra_traits",  type: "catalog",  catalog: "all_traits", multi: true },
    { id: "skill_focus",   type: "select",   options: ["balanced", "combat", "magic", "social", "service"] },
    { id: "description",   type: "longtext" },
  ],
  build: (answers, ctx) => mapToWorkerJSON(answers, ctx),
  post_to_editor: true,
};
```

### 5.2 Initial recipe catalog

- **Workers:** `unique_worker`, `procedural_worker_template`, `monster_worker`
- **Events:** `worker_specific_event`, `event_chain_2_steps`, `building_event_with_skill_check`, `recruitment_event`
- **Daily stories:** `daily_story_basic`, `daily_story_with_trait_roll`, `daily_story_with_loot` — **all three include a mandatory "Requirements" step** (`stat_requirements`, `libido`, `required_traits`, `excluded_traits`, `worker_gender_requirement`, `nsfw_only`). The step is mandatory in flow; individual fields are optional and can be left blank.
- **Interactions:** `simple_interaction`, `trait_granting_interaction`, `worker_specific_interaction`
- **Items:** `equipment_item`, `consumable_item`, `quest_item`
- **Traits:** `permanent_trait`, `temporary_trait` (same trait schema; `temporary_trait` defaults a non-zero `duration` placeholder for use in interaction/event effects)
- **Buildings:** `simple_building_type`, `add_profession_to_building`

### 5.3 Wizard UX

- One question per screen with `Back / Skip (if optional) / Next`.
- Progress bar at top with clickable section labels (lets the user jump back to any answered step).
- Each field has a `?` tooltip opening a side panel with the long-form explanation from the modding guide.
- Live JSON preview is collapsible on the right; it updates in real time as answers are filled in.
- **Final step is always "Review & save":** shows the full JSON, an **editable filename input** prefilled with the recipe's default (`workers_<modname>_unique.json`). If the user clears the input, the default is used. Two buttons: **Save directly** or **Open in full editor** for fine-tuning before saving.

### 5.4 Language

All UI strings, tooltips, labels, recipe titles, and recipe descriptions are in **English only**. JSON keys are unchanged from the game schema (already English).

## 6. Free editor

A wizard-style section-based editor with free navigation between sections. Used to fine-tune recipe output or to edit existing JSONs end-to-end.

### 6.1 Layout

```
┌──────────────────────────────────────────────────────────────────────┐
│  📂 Open  💾 Save  ➕ Add entry  🗑 Delete  ✓ Validate  ⚙ Settings   │
├──────────────┬───────────────────────────────────────────────────────┤
│  Entries     │   [Basic] · [Targeting] · [Conditions] · [Choices]    │
│              │   [Images] · [Review]      progress: ▮▮▮▯▯▯            │
│  • a_quest_1 │                                                       │
│  • a_quest_2 │  ┌─ Section 3 of 6: Conditions & Flags ────────────┐  │
│  • elven_rec │  │ start_when    [______________________]          │  │
│  + Add new   │  │ stop_when     [______________________]          │  │
│              │  │ required_flags [ chips, + add ]                 │  │
│              │  │ excluded_flags [ chips, + add ]                 │  │
│              │  └─────────────────────────────────────────────────┘  │
│              │   ◀ Back · Skip · Next ▶                              │
│              │   [⬇ Show full JSON preview]                          │
└──────────────┴───────────────────────────────────────────────────────┘
```

### 6.2 Behavior

- **Tabs/breadcrumbs at top** are clickable for free navigation; **Back/Next** at bottom support linear authoring.
- **Progress bar** fills sections that have at least one non-neutral edit.
- **Left sidebar** lists entries in the open file; click selects and loads in the editor.
- **Ctrl+K** opens a fuzzy field finder across the schema (jumps to section + scrolls to field).
- **Field types** supported by the generic form renderer:
  - `text`, `longtext` (textarea), `int`, `float`, `bool`
  - `enum` (select)
  - `catalog` (autocompletable dropdown, single or multi)
  - `list_of_strings` (chips)
  - `list_of_objects` (repeatable subform, e.g. `choices`, `loot.bonus_items`)
  - `dict_of_numbers` (key-value editor, e.g. `skill_modifiers`)
  - `formula` (monospace text; a later milestone may add a tester)
- **Modified vs neutral indicator:** small dot next to each field — gray = unedited, blue = user-modified. Per the existing modding guide rule ("every entry includes all keys for its type, even when neutral"), unedited fields **are still serialized** with their neutral default (`null` / `[]` / `{}` / `0` / `false`). The dot is purely a visual aid to show what the modder has actively touched.
- **Unknown keys preservation:** if the loaded JSON has keys not declared in the schema (forward compatibility), they are surfaced in an "Unknown keys" section and round-tripped untouched on save.
- **Key order on save** preserves the loaded file's order where possible (for clean git diffs).
- **Type detection on file open:** the editor infers entity type primarily from the file path (`data/workers/*` → workers, `data/events/*` → events, `data/buildings/*` → buildings or daily-story extensions, etc.). If the path is ambiguous (e.g. file opened from outside the game folder), it falls back to shape detection (e.g. presence of `choices` array → event, `professions` key → building) and, as a last resort, prompts the user to pick the type.

### 6.3 Save flow

- Recipe output → modal: **Save directly** or **Open in full editor** before saving.
- Free editor save: editable filename input on the Review section, default = the loaded file's name (or a recipe default for newly-created entries). Merge logic: append to top-level array, or merge by `id` for object-of-id structures (mirrors what the game does at load time).

## 7. Catalogs and validation

### 7.1 Catalogs

Built in memory on app start from `<game>/game/data/`:

| Catalog | Source | Used in |
|---|---|---|
| `all_traits` | `traits/*.json` merged | required_traits, excluded_traits, add_trait, remove_trait, trait_chance, positive_traits, negative_traits |
| `race_traits` | `traits_races.json` | worker race selection in recipes |
| `all_items` | `items/*.json` → `items` array | give_item, item_id, loot.bonus_items |
| `all_skills` | hardcoded canonical 25 + scan of `building_types.json`'s `skill_name` | condition, skill_modifiers, required_building_worker_skill |
| `all_buildings` | `building_types.json` + `special_buildings.json` | building_type, required_active_professions context |
| `all_professions` | `professions` inside each building | required_active_professions, forbidden_active_professions |
| `all_worker_folders` | `images/workers/*/` directory listing | specific_worker_images, worker.folder |
| `all_worker_names` | `workers/*.json` merged | worker_name, specific_workers |
| `all_event_flags` | regex scan of `event_flags` keys across `events/*.json` + `interactions/*.json` | required_flags, excluded_flags, effect.event_flags (autocomplete + free-text "Custom flag") |
| `names_lists` | `names.json` keys | worker.names_list |

If no game folder is selected, the app falls back to snapshots committed in `devkit_web/src/catalogs/*.json` (regenerated by `scripts/bake_catalogs.mjs` on each release). A yellow banner shows: *"Working from bundled catalogs. Open your game folder to use live data."*

### 7.2 Schemas

Schema definition format is a lightweight custom DSL (not full JSON Schema — simpler and more focused on this app's needs):

```js
export const event_schema = {
  fields: {
    id: { type: "string", required: true, unique_in_file: true },
    weight: { type: "int", min: 0 },
    event_probability: { type: "int", min: 0, max: 100 },
    worker_name: { type: ["string", "list_of_strings", "null"] },
    specific_worker_images: { type: "list_of_strings", catalog: "all_worker_folders" },
    building_type: { type: "list_of_strings", catalog: "all_buildings" },
    required_traits: { type: "list_of_strings", catalog: "all_traits" },
    choices: { type: "list_of_objects", schema: "choice_schema", min_length: 1 },
    // ...
  },
  rules: [
    { id: "image_exists",
      check: (e, ctx) => !e.background_image || ctx.image_exists(e.background_image),
      severity: "warning",
      message: "background_image file not found in game/images/" },
    { id: "trait_exists",
      check: (e, ctx) => e.required_traits.every(t => ctx.catalogs.all_traits.has(t)),
      severity: "error",
      message: "Some required_traits don't exist in any traits file" },
    { id: "guaranteed_implies_weight_zero",
      check: (e) => !e.guaranteed || e.weight === 0,
      severity: "warning",
      message: "guaranteed events ignore weight; consider setting weight: 0" },
  ],
  legacy: {
    required_trait: { migrates_to: "required_traits", as: (v) => [v] },
  },
};
```

**Rule context (`ctx`)** passed to every `check` function exposes:
- `ctx.catalogs` — the live catalog maps from §7.1 (`all_traits`, `all_items`, `all_buildings`, etc.) as `Set`s for fast lookup.
- `ctx.image_exists(path)` — `true` if a file exists under `<game>/game/images/` or `<game>/game/gui/` (uses the File System Access handle).
- `ctx.file` — the current file path and its parsed contents (for cross-entry checks like `unique_in_file`).
- `ctx.entry_index` — position of the current entry within the file (for error reporting).

Schemas are the **canonical source of truth** for the modding guide. `scripts/generate_schema_docs.mjs` regenerates `docs/json_schema_canonical.md` and `user_docs/guides/modding_guide.md` from them, so the docs and the validation can never drift.

### 7.3 Validation tiers

1. **Inline while editing:** red border on invalid fields + tooltip with the rule's message. Never blocks.
2. **Explicit "Validate" button:** side panel listing errors and warnings across every entry in the open file. Click an item to jump to the offending field. Also runs the ported rules from `tools/validate_event_mechanics.py` (e.g. skill checks without `threshold`, missing outcome branches in deterministic daily stories, `worker_gender_requirement` on pool events).
3. **On save:** if `errors > 0`, a modal asks for confirmation ("3 errors found. Save anyway?"). Warnings do not block.

### 7.4 Legacy field auto-migration

When a legacy field is detected (`required_trait` string instead of `required_traits` list, etc.), validation shows a warning with a **"Click to auto-migrate"** action. Click executes the declared `legacy[].as` transform in-place.

## 8. Whoremaster converter

A dedicated tab (not a wizard) that batch-imports `.girlsx`, `.rgirlsx`, `.itemsx`, and `.traitsx`. Functional parity with `_do_wm_import` from `fantasy_manager_editor_v6.py`, with these UX improvements.

### 8.1 Flow

**Step 1 — Source:** drag-and-drop a WM folder or pick it via File System Access. App scans recursively, reports counts and missing image folders.

**Step 2 — Settings:**
- Mod name (output prefix)
- `WM_SKILL_SCALE_MAX` (100 or 70)
- Default cost for unique workers
- Procedural cost range
- Default race trait when none detected (e.g. "Human")
- Toggles: rename images on import, GIF→WebM conversion, copy images into `<game>/game/images/workers/<folder>/`, generate worker stub for characters without image folder.

**Step 3 — Review per character:** sortable table with one row per character. Each row shows the resulting name, race trait, file kind (unique/procedural), top skills with mapping arrows, traits with mapping arrows, image folder summary. Unknown trait/skill mappings show ⚠ with an inline "Resolve" action that opens a modal with similarity-scored suggestions from the live `all_traits` catalog. Resolutions are learned for the rest of the batch and persisted in `localStorage` (and exportable as `mappings.json` for sharing).

**Step 4 — Import:** shows the file plan (which JSONs and image folders will be written) and offers **Save directly** (File System Access) or **Download ZIP** (mirrored folder structure ready to drop into `game/`).

### 8.2 Mapping tables

Skill mapping (`NormalSex → Sex`, `Magic → Craft`, `Performance → Charm`, etc.) and trait mapping (`Cool Person → Charming`, `Big Boobs → Large Breasts`, etc.) live as editable JSON inside the app, seeded from the v6 tables. The modder can extend either table via an in-app editor; changes are persisted per project and exportable.

`TRAIT_REQUIREMENTS` (e.g. "Strong Magic" requires the "Magical" race trait) is preserved from the v6 logic.

### 8.3 Carry-over decisions from v6

- `.girlsx` → `unique: true, encounter_only: true, procedural: false`
- `.rgirlsx` → `unique: false, encounter_only: false, procedural: true` + `names_list: "western_female"`
- `AskPrice` → `comfort_desired` (1–5) via 200-step buckets
- Race traits replace the default "Human" trait when mapped (Elf, Dwarf, Demon, Angel, Vampire, Orc, Goblin, Transformed)
- Baseline skills (20–30 main, 18–32 specialty) generated, then overwritten only where WM explicitly specifies a skill

### 8.4 New in this version

- **Per-character live preview** of the resulting JSON in step 3.
- **Unknown-mapping resolution UI** with similarity suggestions.
- **Duplicate detection** against the loaded `all_worker_names` and `all_worker_folders`; per-row choice of skip / rename / overwrite.
- **Auto-generated trait stubs:** if the user confirms an unmapped WM trait as "new", the converter optionally adds a placeholder entry to `traits_<modname>.json` with empty modifiers and `description: "Imported from Whoremaster"`, ready for the modder to flesh out in the trait editor.
- **`.itemsx` and `.traitsx` fully supported** (the v6 had partial coverage).
- **Output never collides:** all generated files use the `<modname>` prefix; the converter detects collisions inside the user's own mod files and offers merge / replace / skip per entry.

## 9. Image utilities

Three independent tools under a "Tools" tab. None require running the WM converter.

### 9.1 Batch rename

- Drag-and-drop folder or pick via File System Access.
- Applies the v6 `WM_IMAGE_RENAME_PATTERNS` (regex) → lowercase → cleanup of `(2)` / `_2` / consecutive underscores.
- Preview table (`old_name → new_name`) with per-row exclusion checkbox.
- Detects collisions and suffixes `(1)`, `(2)`, etc. — same behavior as `rename_wm_images_in_folder`.
- Apply via File System Access; Firefox fallback exports a `rename_script.sh` / `.bat`.
- Patterns are editable in-app (same editor as the WM mapping tables) for non-WM naming styles.

### 9.2 GIF → WebM (ffmpeg.wasm)

- Lazy-loads the ffmpeg-core bundle on first use (~25MB), with a progress bar. Cached in IndexedDB for instant reopen.
- Drag-and-drop GIFs or pick a folder.
- Settings: bitrate (default 1M), CRF (default 30), `-c:v libvpx-vp9` (same preset as `convert_gif_to_webm` in v6).
- Queue with per-file progress and ETA.
- Output: writes `.webm` next to the `.gif` (same basename); optional "delete original after conversion".

### 9.3 Create worker from image folder

- Pick a folder under `<game>/game/images/workers/<folder>/`.
- Scans filenames and pre-fills the `unique_worker` recipe:
  - `folder` = directory name
  - `nsfw: true` if NSFW-keyworded images are present (`sex_`, `bdsm_`, `oral_`, etc.)
  - Skill suggestions bumped based on present categories (e.g. many `combat_*` → Combat 40 baseline)
- Launches the wizard with those answers pre-populated for the modder to refine.

## 10. Packaging and distribution

Three channels, all from the same `devkit_web/src/` source.

### 10.1 GitHub Pages

- A GitHub Actions workflow on `main` runs `bake_catalogs.mjs`, then publishes `devkit_web/src/` to `gh-pages`.
- Public URL (e.g. `horologist1.github.io/fantasy-manager/devkit/`).
- Always reflects the latest game data.

### 10.2 Offline ZIP in releases

- Release workflow packages `devkit_web/src/` (with baked catalogs) into `fm_devkit_web_<version>.zip`.
- Attached to each game release.
- Double-click `index.html` to launch; works 100% offline (ffmpeg.wasm bundled, no external CDN).

### 10.3 Bundled with the game

- The game build includes `tools/fm_devkit_web/` with the matching version.
- A new entry in the main menu ("Open Modding Tools") opens the local `file://` URL via the OS default browser.

### 10.4 Versioning

- Devkit releases tagged with the matching game version (e.g. `devkit-v0.9.5.5`).
- Banner in the app on game-folder open: *"Built for game v0.9.5.5. You're using v0.9.5.7 — bundled catalogs may be stale. Open your game folder for live data."*
- Mismatch detected by comparing a `game/version.json` file (added by the release workflow) against the baked-in build version.

### 10.5 CI

- JS tests run on GitHub Actions via Node (no headless browser required).
- Every recipe is invoked with synthetic inputs; the resulting JSON is validated against the corresponding schema.
- Golden tests of the WM converter run against committed `.girlsx` / `.rgirlsx` / `.itemsx` fixtures.
- Lint: ESLint (minimal config) + Prettier.

### 10.6 Deprecation of the Python devkit

- `devkit/` is retained for 1–2 game releases as a fallback.
- Its README gains a banner pointing to `devkit_web/`.
- No new features land in `devkit/`; only critical bugfixes.

## 11. Out of scope (for this spec)

- Runtime mod manager UI inside the game (game-side enabling/disabling of installed mods).
- Image generation (only conversion and renaming; no AI image synthesis).
- A Ren'Py-script editor (this devkit only authors content JSON).
- Localization of the devkit UI beyond English.
- Live multi-user co-editing.
- Built-in mod sharing / browsing of community mods.

## 12. Open questions

- Public hosting URL: the exact GitHub Pages path (`/devkit/` vs `/`) and whether to use a custom domain.
- Whether to ship a one-time "First run" tour walking through the four action tiles, or rely solely on inline tooltips.
- Whether to expose the schema DSL itself to power users for adding their own field types (likely deferred to a later milestone).
